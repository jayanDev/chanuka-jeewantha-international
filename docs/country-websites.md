# Country websites

Implemented 9 September 2026. The existing global website remains available at `/`.

Country homepages follow the main homepage's navy/gold visual language, large serif heading, prominent founder portrait and paired enquiry/package actions. Country-specific copy remains independent; guarantees and unverified ranking claims are not copied into these editions. Robots rules explicitly allow all market prefixes and point to the sitemap containing the complete URL list.

## SEO, AEO and GEO implementation

- Server-rendered, country-specific headings, descriptions, FAQ answers and complete article text.
- Self-canonical country URLs and reciprocal `hreflang` links to equivalent pages. Country homepages and the global homepage share the home alternate cluster; the global homepage is `x-default`.
- All 180 URLs in the main sitemap, with equivalent-page language alternates.
- WebPage, Service, BreadcrumbList, visible FAQPage and BlogPosting structured data. Converted reference prices are not represented as binding structured-data offers.
- A concise answer near the beginning of each article, contextual examples, source links, a named author and an editorial date.
- Visible remote-service and English-language scope. Regional `areaServed` describes the market, not an invented office address.
- A country selector that preserves the current section or article topic. No IP-based redirects, cloaking or hidden keyword lists.
- Country catalogue and service CTAs keep the visitor inside the same country enquiry route.

References: [Google multi-regional guidance](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites), [Google AI features guidance](https://developers.google.com/search/docs/appearance/ai-features), [Google spam policies](https://developers.google.com/search/docs/essentials/spam-policies). Technical markup helps discovery and interpretation; it does not guarantee indexing, rich results, rankings or AI citations.

## Pricing and maintenance

The user supplied USD prices, not independently approved country price lists. Individual services use the existing `signaturePrices` export from `src/lib/packages-catalog.ts`. The five country bundles keep the approved USD amounts (179, 349, 499, 899, 1499).

`src/lib/market-rates.ts` holds a checked USD reference snapshot from [ExchangeRate-API](https://open.er-api.com/v6/latest/USD), timestamp 2026-09-09 00:02:31 UTC. The website does not require this API at runtime. USD remains exact; non-USD prices are labelled estimates. OMR and KWD keep three decimal places and VND uses whole-unit formatting. The final invoice, applicable taxes/fees and supported payment method must be confirmed after review.

Update the snapshot and date together when rates are refreshed. Do not change the rates to disguise an independently chosen price list. If fixed local prices are wanted later, approve and maintain them as explicit prices. The existing global site's currency selector remains a separate legacy display path; country pages never use its IP detection or saved preference.

Russia enquiries explicitly require confirmation of service/payment availability; RUB display does not promise a payment provider. No unsupported international payment methods are advertised by the new pages.

## Form and operational setup

The existing Web3Forms enquiry service is reused. A country enquiry records its country page, target market, chosen package and display currency, along with the visitor's existing fields. CV upload remains optional and uses the current provider's attachment flow. No test enquiry should be sent to the business as part of automated checks; tests intercept the submission.

Before promoting these editions:

1. Review the market examples and founder-authored article copy for editorial sign-off.
2. Confirm the production Web3Forms account accepts attachments and delivers messages to the intended inbox. Existing account/key are unchanged.
3. Confirm invoice currencies, payment availability and any applicable fees/taxes when responding to an enquiry.
4. Submit the updated `/sitemap.xml` in Search Console and inspect representative country URLs. No separate domains or DNS records are required for path-based editions.
5. Measure country/query impressions and actual enquiries after indexing. Track answer-engine citations separately before making GEO ranking claims.

Source map: light route configuration in `src/lib/markets.ts`; unique market guidance in `src/content/market-editorial.ts`; article composition in `src/lib/market-articles.ts`; pricing in `src/lib/market-pricing.ts`; metadata/schema/sitemap in `src/lib/market-seo.ts`; shared UI in `src/components/markets/`; routing extends the existing `[landingSlug]` segment to avoid Next.js dynamic-segment conflicts.

Run the existing unit tests without the database-push pretest hook:

```sh
npx vitest run --pool=threads --maxWorkers=1
npm run lint
npm run build
npm run start -- -p 3100
node scripts/verify-country-sites.cjs
```

The browser check uses Node.js 24's built-in TypeScript support and defaults to `http://localhost:3100`; set `COUNTRY_TEST_URL` to test another local preview. It checks all 180 URLs, canonicals, headings, language alternates, structured data, local-currency tables, internal country links, sitemap entries and invalid-route HTTP status codes. It also checks desktop, tablet and narrow mobile layouts, country switching, package selection and intercepted form submissions. No business enquiry is sent. Reports and screenshots are written to the ignored `test-results/country-sites/` directory.

The country-only proxy guard returns real HTTP 404 responses before Next.js starts streaming unknown country routes. Existing authentication redirects are covered by regression tests. The global header now uses its mobile menu on tablet widths, and the shared booking embed fits narrow screens.
